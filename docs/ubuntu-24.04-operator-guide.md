# Руководство оператора: RX-PRO S3 Manager на Ubuntu 24.04

Практическое руководство для администратора, который разворачивает и ведёт
**RX-PRO-S3-Manager** на отдельном VPS с **Ubuntu 24.04 LTS**. Документ дополняет
`README.md` и описывает рабочий цикл целиком: подготовка VK Cloud → установка →
первичная настройка → ежедневные операции → диагностика → обновление.

> **Статус выпуска.** Текущая версия — `0.1.0-rc2`, **тестовый выпуск, не
> production-релиз**. Для первой проверки рекомендуются Ubuntu 24.04 x86_64,
> systemd, 2 GiB RAM и **отдельный тестовый бакет** в отдельном проекте VK.
> APK RX-PRO не изменяется. HTTPS-подписки и iOS в эту версию не входят.

Документ **не** заменяет официальные инструкции VK Cloud по аккаунтам, ключам и
бакетам; ссылки на них приведены в `README.md`.

## 3. Подготовка VK Cloud

Ключевой момент — **два разных типа ключей**. Их нельзя путать:

| Где получен ключ | Для чего используется |
|---|---|
| **Object Storage → Аккаунты** | Административная пара Access Key ID + Secret Key для менеджера |
| **Ключи доступа внутри бакета** | Бакетные/префиксные ключи; менеджер сам создаёт их для пользователей |

В мастер передаётся **ключ аккаунта Object Storage**, а не бакетный/префиксный
ключ, не пароль от сайта VK Cloud, не токен проекта и не токен GitHub.

1. **Проект и регион.** Откройте кабинет VK Cloud Москва, выберите проект с
   оплатой. Используется **Object Storage Москва / `ru-msk`**. Всё дальнейшее —
   в одном проекте и регионе.
2. **Аккаунт Object Storage.** Создайте отдельный аккаунт для менеджера и
   сохраните **одну** пару Access Key ID + Secret Key. Секрет показывается только
   при создании. Не смешивайте ID одной пары с Secret Key другой.
3. **Бакет.** Либо создайте бакет в кабинете (STANDARD/Hotbox, **приватный**, без
   версионирования и Object Lock, без точек в имени), либо разрешите менеджеру
   создать его в мастере. `403` при проверке **не считается** отсутствием бакета.

Подробные пошаговые шаги с формулировками вопросов мастера — в `README.md`,
раздел «Подготовка VK Cloud».

## 4. Установка или продолжение с GitHub

Подключитесь к VPS по SSH и вставьте блок **целиком**:

```bash
sudo apt-get update && sudo apt-get install -y curl ca-certificates && (
  set -e
  f="$(mktemp)"
  trap 'rm -f "$f"' EXIT
  curl -fsSL --proto '=https' https://raw.githubusercontent.com/cwash797-cmd/RX-PRO-S3-Manager/main/get.sh -o "$f"
  sudo bash "$f"
)
```

Загрузчик скачивает **закреплённый release-архив**, проверяет SHA256 и manifest,
ставит зависимости, обновляет файлы менеджера и запускает мастер.

- **Не используйте `curl | bash`** — мастеру нужен интерактивный терминал.
- При повторном запуске собственная панель и сохранённые настройки остаются на
  месте; панель заново не устанавливается.
- Уже подтверждённые ответы сохраняются в root-only файле `0600` сразу после
  подтверждения, ещё до ввода ключей.

**Если установка прервалась — не переустанавливайте VPS, не удаляйте бакет и не
очищайте `/var/lib/rxs3`.** Просто повторите блок выше; мастер распознает
незавершённую установку и продолжит её.

## 5. Первичная настройка (мастер)

Мастер последовательно спросит:

1. локальный порт панели — по умолчанию **2053** (при чистой установке);
2. локальный порт S3-входа — по умолчанию **10001**;
3. **Access Key ID аккаунта** из раздела 3;
4. **Secret Key той же пары**;
5. **точное имя бакета**;
6. разрешение создать бакет, только если его ещё нет — **да** или **нет**.

Поведение ввода:

- Ввод ключей скрыт: даже звёздочки не отображаются. Вставьте значение один раз
  и нажмите Enter.
- В вопросе «да/нет» пустой Enter означает **нет**; опечатка будет запрошена
  повторно.
- **Не вставляйте ключи** в команды, чаты и сообщения поддержки.

Проверки, которые менеджер выполняет сам перед выдачей пользователей:
`ListBuckets` (ключ аккаунта), `HeadBucket` (доступ к бакету),
приватность/настройки и `ListPrefixKeys` (право управлять префиксными ключами).

## 6. Проверка после установки

```bash
# Состояние установки (в т.ч. незавершённый мастер)
sudo rxs3 status

# Фактически сохранённые порты
sudo rxs3 ports

# Адрес и пароль новой панели (НЕ присылать в поддержку)
sudo rxs3 panel-info

# Готовая установка: диагностика
sudo rxs3 diagnose

# Службы
sudo systemctl is-active x-ui rxs3-sync.timer
```

Для панели на порту 2053 откройте SSH-туннель со своего компьютера:

```bash
ssh -L 2053:127.0.0.1:2053 root@IP_VPS
```

Затем откройте локальный URL с base path, который показывает `panel-info`.

## 7. Ежедневные операции

| Задача | Команда / действие |
|---|---|
| Продолжить прерванный мастер | `sudo rxs3 setup` |
| Исправить ключи/бакет (только до завершения первичной настройки) | `sudo rxs3 setup --edit-vk` |
| Открыть меню готовой установки | `sudo rxs3` |
| Синхронизировать панель | `sudo rxs3 sync` |
| Диагностика | `sudo rxs3 diagnose` |
| Резервная копия | `sudo rxs3 backup /root/manager_backup.rxs3-backup` |
| Восстановление в карантин | `sudo rxs3 restore-quarantine /root/manager_backup.rxs3-backup /root/rxs3_quarantine` |

**Выдача и отзыв пользователей** выполняется через меню: выдача ссылок/QR,
отключение, включение с новой ссылкой, ротация и удаление доступа, синхронизация.

- Отзыв независимо останавливает bridge, отключает клиента и отзывает PAK
  с проверкой.
- `revocation_pending` — это **незавершённый отзыв**, а не успех: после
  восстановления API повторите `sudo rxs3 sync`.
- API-сбой не приравнивается к пустому списку; незавершённая выдача не
  возобновляется автоматически. Удалённые записи не включаются обратно.

**Резервные копии.** Пароль вводится скрыто (от 12 символов), используются scrypt
и AES-256-GCM. Копия содержит **реестр/настройки менеджера**, но не образ VPS и не
БД 3x-ui. Восстановление идёт в новый офлайн-каталог карантина и ничего не
включает и не перезаписывает живую установку. Базу панели сохраняйте отдельно.

## 8. Порты и сеть

| Назначение | По умолчанию | Доступ |
|---|---|---|
| Веб-панель при чистой установке | `127.0.0.1:2053/TCP` | Только локально; администрирование через SSH-туннель |
| Управляемый S3-вход панели | `127.0.0.1:10001/TCP` | Только локально, для bridge |
| VK Object Storage | исходящий `443/TCP` | HTTPS к облаку; входящий порт VPS не нужен |

Первые два порта выбираются в мастере; занятые порты отклоняются. Для
существующей панели её адрес/порт и другие настройки **не меняются**.

**Другие конфигурации можно добавлять на свободных портах.** Не меняйте и не
переиспользуйте управляемый S3-вход, его локальный адрес, порт и ключ VLESS
Encryption. Firewall, SSH, nginx/Caddy и посторонние службы менеджер не
перенастраивает. Публичные VPN-порты для S3 открывать не надо. Число `11600` во
внутренней XDRIVE-конфигурации не означает публичный TCP-listener.

## 9. Диагностика ошибок VK

Пример сообщения: `VK S3: ListBuckets: HTTP 403 (InvalidAccessKeyId)`. Тело ответа,
секреты и строка подписи не выводятся; код берётся только из фиксированного
безопасного списка. У HEAD-запроса код в теле часто отсутствует.

| Этап / код | Что проверить |
|---|---|
| `ListBuckets`, `InvalidAccessKeyId` | Активный ключ именно аккаунта, правильный проект и регион Москва |
| `SignatureDoesNotMatch` | ID и Secret из одной пары без лишних символов; также время VPS |
| `RequestTimeTooSkewed`, `RequestExpired` | Дату и синхронизацию времени: `timedatectl status` |
| `HeadBucket: 403` после успешного `ListBuckets` | Точное имя, доступ этого аккаунта к бакету; возможно, имя принадлежит другой учётной записи |
| `GetBucketAcl/Policy/Versioning: 403` | Права читать настройки бакета; не обходить проверку приватности |
| `ListPrefixKeys: 403` | Права управлять PAK; бакетного ключа для менеджера недостаточно |

По одному `403` точную причину установить нельзя. Менеджер не обходит отказ доступа
и не включает публичность. Исправьте параметры через `sudo rxs3 setup --edit-vk`.
Созданные ранее бакеты при этом не удаляются. Если ошибка остаётся, пришлите только
название операции, HTTP-статус и безопасный код.

## 10. Обновление и повторная установка

Повторный запуск установочного блока обновляет менеджер и **сохраняет** уже
установленную панель и данные менеджера. Для скачивания без установки:

```bash
bash get.sh --download-only ./rxs3-reviewed
```

Выпуск публикуется после успешной проверки исходного коммита в CI.

**PR #3 пока не выпущен.** Публичный установщик не применяет его миграцию.
В подготовленной миграции публичное поле «Шифрование» заполняется существующим
ключом, а комментарии получают имя пользователя без смены технического email.
UUID, PAK, ссылки, квоты и сроки сохраняются. Перезапускаются только подходящие
активные bridge; отключённый/удалённый доступ не включается заново. Планируйте
окно обслуживания: обновление inbound может также перезапустить ядро панели.

Новый сервер завершает сессии без признаков живого клиента после 180 секунд
плюс время проверки хранилища. Это касается и полностью простаивающих соединений.
Активная загрузка поддерживает сессию подтверждениями получения сегментов.
Online-индикатор панели имеет собственную задержку; после выключения VPN bridge
продолжает опрос S3 для новых сессий. Квота VPN-трафика не ограничивает оплату S3.

## 11. Нативная сборка (Xray + S3-бэкенд) — для разработчиков

Серверный harness находится в этом репозитории: `native/build.py` скачивает
закреплённый Xray, добавляет S3-бэкенд и watchdog, проверяет модули и собирает
**только Linux-сервер**. Android APK не пересобирается. Нужен Go **1.27.1**.

```bash
python3 native/build.py test       # полный xdrive/S3 suite с race detector
python3 native/build.py linux      # .lab/native/bin/xray-s3
python3 native/package.py          # архив, SHA256, лицензии и хеши исходников
```

Для проверки совместимости нужен **неизменённый бинарник из RX-PRO 1.6.0**;
его проверенный архив имеет SHA256
`5c25988b6878a0adc0300521f2c428febc90cd52aeaa6a5b9e463fc8f1db4618`.

```bash
python3 native/integration.py --client /путь/к/старому/xray-s3 --server .lab/native/bin/xray-s3
```

Тест использует локальное объектное хранилище, mux и реальный VLESS Encryption:
загрузка переживает TTL, а принудительное завершение старого клиента приводит
к закрытию upstream-сессии. Настоящий VK этим тестом не проверяется.

Нативные проверки прошли локально. Добавление отдельной задачи в GitHub Actions
пока заблокировано отсутствием у интеграции права **Workflows: write**. Текущий
workflow проверяет Python, реальную панель и установку, но ещё не новый watchdog.
До завершения CI и публикации серверного компонента `get.sh` остаётся на rc2,
а `apply-upgrade` не выдаёт старый сервер за обновлённый.

## 12. Безопасность и гигиена секретов

**Никогда не публикуйте:** ссылки/QR, ключи доступа, `config.json`, `setup.json`,
`state.sqlite`, runtime-файлы, пароли резервных копий, вывод `panel-info`.

`diagnose` намеренно формирует отчёт без ссылок, ключей и тела ответов VK; его
можно передать для диагностики, предварительно просмотрев содержимое. Не заменяйте
его дампом конфигураций, базы или полными журналами.

- Бакет остаётся **приватным**: без публичного чтения/записи, публичных ACL,
  bucket policy, website hosting и CDN.
- Административный ключ аккаунта не передаётся в Android или процесс bridge.
- Для каждого пользователя менеджер создаёт отдельный UUID, отдельный префикс
  поколения `rxs3/<установка>/<пользователь>/gN/` и две отдельные PAK-пары
  (Android и серверный bridge).
- Квота 3x-ui — **не** лимит оплаты S3. Следите за расходами Object Storage.

## 13. Известные ограничения

CI проверяет unit/security-сценарии, настоящую установку и systemd на Ubuntu
22.04/24.04, повтор установки, реальный API 3x-ui, сохранность соседних
конфигураций, обрыв на вводе ключа, отказ VK по модели и возобновление журнала rc1.

**Пока не подтверждено:**

- полная установка на Debian VPS (Debian 12 имеет только unit-проверки);
- особенности живого PAK/bucket API (в CI настоящий VK заменён моделью);
- полный путь до Android, перезагрузка VPS и поведение под нагрузкой.

Честная диагностика `403` не означает, что конкретные права вашего аккаунта уже
исправлены. Начните с двух тестовых пользователей, проверьте независимое
отключение и выдачу новой ссылки.
