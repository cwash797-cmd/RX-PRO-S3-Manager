# RX-PRO S3 Manager

**Управление доступом RX-PRO через VK Object Storage на Ubuntu 24.04 LTS.**

Русский терминальный менеджер объединяет **3x-ui 3.9.0**, **RX-PRO 1.6.0**
и приватное хранилище **VK Cloud Москва / ru-msk**: от первоначальной установки
до выдачи пользователей, отзыва ключей и зашифрованных резервных копий.

[Руководство оператора](docs/ubuntu-24.04-operator-guide.md) ·
[Выпуски](https://github.com/cwash797-cmd/RX-PRO-S3-Manager/releases) ·
[Проверки CI](https://github.com/cwash797-cmd/RX-PRO-S3-Manager/actions)

## Возможности

- Установка с GitHub без токенов, SCP и ручного переноса каталогов.
- Чистая установка закреплённой 3x-ui или подключение совместимой локальной панели.
- Добавление пользователей, ссылки и QR, отключение, ротация и удаление доступа.
- Отдельные UUID, S3-префиксы и пары Prefix Access Keys для каждого пользователя.
- VLESS Encryption между клиентом и панелью; административные ключи не попадают в профиль.
- Возобновляемая настройка, диагностика VK и синхронизация ограничений панели.
- Зашифрованные копии реестра и офлайн-восстановление в карантин.

```text
RX-PRO → HTTPS / VK Object Storage → изолированный bridge → локальная 3x-ui → Интернет
```

Входящий публичный VPN-порт для S3 не требуется. Панель при чистой установке
доступна только локально, через SSH-туннель. Соседние inbound, firewall и SSH
менеджер не перенастраивает.

## Требования

| Компонент | Требование |
|---|---|
| VPS | Ubuntu 24.04 LTS, x86_64, systemd, рекомендуются 2 GiB RAM |
| Права | root или sudo |
| Сеть | исходящий HTTPS к GitHub и VK Object Storage |
| Хранилище | приватный бакет Москва / ru-msk и ключ аккаунта Object Storage |
| Клиент | RX-PRO 1.6.0 для Android; APK менять не нужно |

Ubuntu 22.04 также проходит установочные проверки CI. Debian 12 пока проверяется
только на уровне unit-тестов. Ограничения и статус выпуска приведены ниже.

## Установка или продолжение прямо с GitHub

Подключитесь к VPS по SSH и вставьте блок **целиком**. GitHub-токены и ручной перенос
файлов не нужны. Если 3x-ui уже установлена сторонним способом, загрузчик спросит,
подключить ли её, и не переустановит её автоматически. Нужна обычная локальная
3x-ui **3.9.0** в стандартном `/usr/local/x-ui`, не Docker.

```bash
sudo apt-get update && sudo apt-get install -y curl ca-certificates && (
  set -e
  f="$(mktemp)"
  trap 'rm -f "$f"' EXIT
  curl -fsSL --proto '=https' https://raw.githubusercontent.com/cwash797-cmd/RX-PRO-S3-Manager/main/get.sh -o "$f"
  sudo bash "$f"
)
```

Загрузчик скачивает **закреплённый release-архив**, проверяет SHA256 и manifest,
ставит зависимости, обновляет файлы менеджера и запускает мастер. При повторе
собственная панель и сохранённые настройки остаются на месте. При прерывании уже
подтверждённые ответы сохраняются в root-only файле 0600.
Не используйте `curl | bash`: мастеру нужен интерактивный терминал.

Дальше достаточно `sudo rxs3` — незавершённый мастер продолжится, а для готовой
установки откроется меню. Для скачивания без установки можно использовать
`bash get.sh --download-only ./rxs3-reviewed` с новым каталогом.

## Подготовка VK Cloud — что делает администратор

**Папки и файлы вручную создавать не нужно. Бакет должен оставаться приватным.**
Есть два разных типа ключей — это важно:

| Где получен ключ | Для чего используется |
|---|---|
| **Object Storage → Аккаунты** | Административная пара Access Key ID + Secret Key для менеджера |
| **Ключи доступа внутри бакета** | Бакетные/префиксные ключи; менеджер сам создаёт их для пользователей |

В мастер передавайте **ключ аккаунта Object Storage**, а не бакетный/префиксный
ключ, не пароль от сайта VK Cloud, не токен проекта и не токен GitHub.

### Шаг 1. Проект и регион

Откройте [кабинет VK Cloud Москва](https://msk.cloud.vk.ru/app), выберите нужный
проект с настроенной оплатой. Используется **Object Storage Москва / ru-msk**.
Весь дальнейший процесс должен выполняться в одном проекте и регионе.

### Шаг 2. Отдельный аккаунт Object Storage и его ключи

1. Откройте **Object Storage → Аккаунты**.
2. Нажмите **Добавить** и задайте понятное имя отдельного аккаунта для менеджера.
   Имя аккаунта не является именем бакета.
3. В появившемся окне сохраните **Access Key ID** и **Secret Key** одной пары.
   Секрет показывается только при создании. Не смешивайте ID от одной пары с
   Secret Key от другой.
4. Если аккаунт уже создан, откройте его и используйте **Добавить ключ доступа**.
   Не удаляйте ключи, которые используются другими приложениями.
5. Убедитесь, что выбранный ключ активен. Не создавайте вместо него ключ во вкладке
   конкретного бакета — это другой уровень доступа.

### Шаг 3. Бакет — выберите один вариант

**Вариант А: администратор создаёт бакет в кабинете (проще для первого знакомства).**

1. В том же проекте и регионе откройте **Object Storage → Бакеты → Создать**.
2. Придумайте уникальное имя: 3–63 строчные латинские буквы, цифры и дефисы.
   Менеджер первой версии не принимает точки в имени. Имя потом нельзя переименовать.
3. Выберите обычный класс **STANDARD / Hotbox**, не архивное хранение.
4. **Не включайте** версионирование и блокировку объектов (Object Lock).
5. Оставьте бакет **приватным**: без публичного чтения/записи, публичных ACL,
   bucket policy, website hosting и CDN. Никакую публичную ссылку получать не нужно.
6. Создайте бакет. Учётная запись, ключ которой вы передадите менеджеру, должна
   иметь административный доступ к этому бакету, включая его настройки и PAK API.
7. В мастере введите **точное имя созданного бакета**. На вопрос
   «Если бакета нет, разрешить менеджеру создать его?» ответьте **нет**.

**Вариант Б: бакет создаёт менеджер.**

Не создавайте его заранее. В мастере задайте новое уникальное имя и ответьте **да**
на вопрос о создании. Будет использована административная пара из шага 2.
Создание разрешается только при подтверждённом отсутствии бакета (`404`).
**`403` не считается отсутствием**: это может быть чужое занятое имя или отказ
доступа. Менеджер в таком случае не пытается присвоить/изменить бакет.

Выбор «да» не делает существующий бакет публичным и не исправляет недостаточные
права ключа. Для теста не используйте рабочий бакет с другими данными.

### Шаг 4. Что вводить на VPS

Мастер спросит:
1. локальный порт панели — по умолчанию **2053** (при чистой установке);
2. локальный порт S3-входа — по умолчанию **10001**;
3. **Access Key ID аккаунта** из шага 2;
4. **Secret Key той же пары**;
5. **точное имя бакета** из шага 3;
6. разрешение создать бакет, только если его ещё нет — **да** или **нет**.

Ввод ключей скрыт: даже звёздочки не отображаются. Вставьте значение один раз и
нажмите Enter. В вопросе «да/нет» пустой Enter означает **нет**; опечатка будет
запрошена повторно. Не вставляйте ключи в команды или сообщения поддержки.

### Шаг 5. Что менеджер делает сам

Сначала выполняются проверка ключа аккаунта (`ListBuckets`), доступа к выбранному
бакету (`HeadBucket`), приватности/настроек и возможности управлять префиксными
ключами (`ListPrefixKeys`). При добавлении пользователя менеджер сам создаёт:

- отдельный UUID в панели;
- отдельный префикс поколения `rxs3/<установка>/<пользователь>/gN/`;
- две отдельные PAK-пары: для Android и для серверного bridge;
- конфигурацию bridge, готовую ссылку и QR для RX-PRO.

Папка в S3 — это префикс имени объекта. Не надо заранее создавать каталоги,
загружать JSON, писать конфиг в бакет или вручную выпускать пользовательские ключи.
Административный ключ аккаунта не передаётся в Android или процесс bridge.

Официальные инструкции VK:
[аккаунт и ключи](https://cloud.vk.ru/docs/ru/storage/s3/instructions/access-management/access-keys),
[создание бакета](https://cloud.vk.ru/docs/ru/storage/s3/instructions/buckets/create-bucket),
[разница типов ключей](https://cloud.vk.ru/docs/ru/storage/s3/concepts/access/account-and-keys),
[PAK API](https://cloud.vk.ru/docs/ru/storage/s3/api/pak).

## Порты и совместимость с другими конфигурациями

| Назначение | По умолчанию | Доступ |
|---|---|---|
| Веб-панель при чистой установке | `127.0.0.1:2053/TCP` | Только локально; администрирование через SSH-туннель |
| Управляемый S3-вход панели | `127.0.0.1:10001/TCP` | Только локально, для bridge |
| VK Object Storage | исходящий `443/TCP` | HTTPS к облаку; входящий порт VPS не нужен |

Первые два порта можно выбрать в мастере; занятые порты отклоняются. Для
существующей панели её адрес/порт и другие настройки не меняются.
Список фактически сохранённых портов: `sudo rxs3 ports` или пункт меню
«Порты и совместимость». Для незавершённой настройки: `sudo rxs3 status`.

**Другие конфигурации можно добавлять на свободных портах.** Не меняйте и не
переиспользуйте управляемый S3-вход, его локальный адрес, порт и ключ VLESS Encryption.
Firewall, SSH, nginx/Caddy и посторонние службы менеджер не перенастраивает.
Публичные VPN-порты для S3 открывать не надо. Число `11600` во внутренней
XDRIVE-конфигурации не означает публичный TCP-listener и не требует правила firewall.

При чистой установке подписки панели выключаются. Панель впервые запускается
в отдельном network namespace, её пароль заменяется до обычного запуска службы.
Адрес и пароль новой панели: `sudo rxs3 panel-info` (не присылайте вывод в поддержку).
Для панели на порту 2053 на своём компьютере откройте туннель:

```bash
ssh -L 2053:127.0.0.1:2053 root@IP_VPS
```

Затем откройте локальный URL с base path, который показывает `panel-info`.

## Если установка прервалась или вы уже получили 403 в rc1

**Не переустанавливайте VPS, не удаляйте бакет и не очищайте `/var/lib/rxs3`.**
Перезагрузка сервера не исправляет ключи доступа.

1. Повторите **целиком** блок установки ниже — он обновит менеджер и распознает
   собственную незавершённую установку. Панель заново не устанавливается.
2. Для проверки этапа выполните:

```bash
sudo rxs3 status
```

3. Для продолжения мастера:

```bash
sudo rxs3 setup
```

4. Если нужно исправить ошибочно введённые ключи или бакет:

```bash
sudo rxs3 setup --edit-vk
```

Последняя команда действует **только до завершения первичной настройки**. Она
не удаляет панель, её пароль, локальные порты или существующие бакеты. После
обновления старого журнала rc1 сохраняются идентификатор установки и уже созданные
ресурсы. Для активной установки смена аккаунта/бакета этим способом запрещена,
чтобы не потерять контроль над действующими ключами пользователей.

Не вводите `--existing-panel` отдельной командой. Временная переменная `$f` из блока
загрузки существует только внутри этого блока: повторно использовать её не надо.

## Если VK вернул ошибку

Пример нового сообщения: `VK S3: ListBuckets: HTTP 403 (InvalidAccessKeyId)`.
Текст/тело ответа, секреты и строка подписи не выводятся; код берётся только из
фиксированного безопасного списка. У HEAD-запроса код в теле часто отсутствует.

| Этап/код | Что проверить |
|---|---|
| `ListBuckets`, `InvalidAccessKeyId` | Активный ключ именно аккаунта, правильный проект и регион Москва |
| `SignatureDoesNotMatch` | ID и Secret из одной пары без лишних символов; также время VPS |
| `RequestTimeTooSkewed`, `RequestExpired` | Дату и синхронизацию времени: `timedatectl status` |
| `HeadBucket: 403` после успешного ListBuckets | Точное имя, доступ этого аккаунта к бакету; возможно, имя принадлежит другой учётной записи |
| `GetBucketAcl/Policy/Versioning: 403` | Права читать настройки бакета; не обходить проверку приватности |
| `ListPrefixKeys: 403` | Права управлять PAK; бакетного ключа для менеджера недостаточно |

По одному `403` точную причину установить нельзя. Менеджер не обходит отказ доступа
и не включает публичность. Исправьте параметры через `sudo rxs3 setup --edit-vk`.
Созданные ранее бакеты при этом не удаляются. Если ошибка остаётся, пришлите только
название операции, HTTP-статус и безопасный код. После готовой установки можно
прислать `sudo rxs3 diagnose`.

## Пользователи, отзыв и резервные копии

Меню позволяет выдавать ссылки/QR, отключать, включать с новой ссылкой, ротировать
и удалять доступ, синхронизировать панель, диагностировать ошибки и создавать
зашифрованные копии. Отзыв независимо останавливает bridge, отключает клиента
и отзывает PAK с проверкой. `revocation_pending` — **незавершённый отзыв**,
а не успех: после восстановления API повторите `sudo rxs3 sync`.
API-сбой не приравнивается к пустому списку; незавершённая выдача не возобновляется
автоматически. Удалённые записи не включаются обратно.

```bash
sudo rxs3 backup /root/manager_backup.rxs3-backup
sudo rxs3 restore-quarantine /root/manager_backup.rxs3-backup /root/rxs3_quarantine
```

Пароль вводится скрыто (от 12 символов), используются scrypt и AES-256-GCM.
Копия содержит **реестр/настройки менеджера**, не образ VPS и не БД 3x-ui.
Восстановление идёт в новый офлайн-каталог карантина, ничего не включает и не
перезаписывает живую установку. Автоматическая миграция и применение старой копии
к работающей установке не реализованы. Базу панели сохраняйте отдельно.

## Шифрование, имена и статус online

В ссылках менеджера уже используется VLESS Encryption (`1rtt`). Пустое поле
«Шифрование» в интерфейсе старой установки само по себе **не означает отсутствие
шифрования**: серверный приватный ключ хранится в «Расшифрование», а публичное
поле панели служит также для отображения и генерации ссылок. Заполнять его новым
ключом вручную нельзя — существующие клиенты используют прежнюю пару.

В PR #3 подготовлена миграция публичного поля и комментариев вида
`RXS3 managed | testvasya`. Технический email, UUID, ссылки, ключи и лимиты
сохраняются. Изменение метаданных может вызвать перезапуск ядра панели.

Там же подготовлен серверный watchdog: сессия без входящих данных и подтверждений
получения ответов завершается после 180 секунд отсутствия прогресса, с задержкой
на проверку хранилища. Активная односторонняя загрузка считается живой по удалению
прочитанных сегментов старым клиентом. Долгие полностью простаивающие соединения
тоже закрываются; приложению может потребоваться переподключение. Это **не**
подмена индикатора online: панель обновляет его отдельно по своей статистике.

**Эти изменения пока не опубликованы в установочном выпуске.** `get.sh` остаётся
на rc2; не устанавливайте черновую ветку вместо проверенного релиза. Команда
`apply-upgrade --yes` в исходниках намеренно заблокирована до закрепления нового
серверного артефакта. После выпуска обновление должно применить миграцию и
перезапустить только действующие управляемые bridge; APK и ссылки останутся прежними.

Заполнение поля шифрования не ускоряет транспорт. Реальная скорость VK и работа
watchdog на живом облаке пока не измерены. Даже при выключенном VPN включённый
bridge опрашивает хранилище в ожидании сессий; нулевой расход S3 не гарантируется.

## Статус выпуска и границы проверки

Публичный установщик закреплён на **0.1.0-rc2**, предварительном выпуске.
Для первого развёртывания используйте отдельный сервер и бакет. HTTPS-подписки,
iOS и автоматическая миграция на другой VPS в эту версию не входят.


[CI](https://github.com/cwash797-cmd/RX-PRO-S3-Manager/actions/workflows/test.yml)
проверяет unit/security-сценарии, настоящую установку и systemd на Ubuntu
22.04/24.04, повтор установки, реальный API 3x-ui, сохранность соседних
конфигураций, обрыв на вводе ключа, отказ VK по модели и возобновление журнала rc1.
Выпуск публикуется после успешной проверки его исходного коммита.

**Настоящий VK в CI заменён моделью.** Пока не подтверждены полная установка на
Debian VPS, все особенности живого PAK/bucket API, полный путь до Android,
перезагрузка VPS и нагрузка. Честная диагностика 403 не означает, что конкретные
права вашего аккаунта уже исправлены. Начните с двух тестовых пользователей,
проверьте независимое отключение и выдачу новой ссылки.
Квота 3x-ui — не лимит оплаты S3. Следите за расходами Object Storage.

Не публикуйте ссылки/QR, ключи, `config.json`, `setup.json`, `state.sqlite`,
runtime-файлы и пароли копий. Код — GPL-3.0; лицензии отдельно скачиваемых
компонентов сохраняются в `/opt/rxs3/licenses`.

Для разработки: `python3 -m unittest discover -s tests -v` и
`python3 build_release.py`. Системные smoke-тесты разрешены только на
специально подготовленном одноразовом CI runner, не на рабочем VPS.
