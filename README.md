# RX-PRO-S3-Manager

Русский терминальный менеджер для **3x-ui 3.9.0**, **RX-PRO 1.6.0** и
**VK Cloud Object Storage Москва / ru-msk**. Отдельный проект; APK не изменяется.

## Первый тестовый релиз: 0.1.0-rc1

**Для первичной проверки на новой VPS и отдельном тестовом бакете, не для рабочего
сервера и массовой выдачи доступа. Это prerelease, а не production-релиз.**

[Скачать release-архив и контрольные суммы](https://github.com/cwash797-cmd/RX-PRO-S3-Manager/releases/tag/v0.1.0-rc1).
Реализованы меню, установщик, первоначальная настройка, жизненный цикл доступа,
синхронизация, диагностика и зашифрованные копии менеджера.

Пройдены локальные и CI-проверки:

- 32 автоматических тестов: журналирование, сбои после удалённых изменений,
  потеря ответа PAK, отключение/ротация/удаление, независимость двух пользователей,
  недоступность панели/облака, устаревший кэш авторизации, приватные файлы,
  блокировка конкурирующих операций, защита архивов, AES-GCM и карантин копий;
- настоящий checksum-pinned бинарник **3x-ui 3.9.0**: смена пароля, выключение
  подписок, создание отдельного inbound, создание двух клиентов, отключение,
  смена UUID и удаление одного без изменения второго;
- бинарник панели в этих тестах запускается только в отдельном network namespace;
- SigV4 независимо сопоставлен с `botocore 1.40.70`, включая пробел, `+`, `/` и Unicode;
- сборка source-only архива с SHA256 без `.lab`, баз, runtime-конфигураций и секретов;
- **Ubuntu 22.04 и 24.04:** настоящая чистая установка в одноразовых CI VM,
  безопасный bootstrap панели, systemd LoadCredential/DynamicUser, запуск и
  перезапуск закреплённого native core, повторная установка без изменения состояния;
  установка проверяется и с ограничительным root umask 077, копирование исходников
  переключает версию атомарно и не активирует недописанный каталог;
- подключение существующей панели с сохранением прежних inbound, WS и настроек;
- полный жизненный цикл менеджера через настоящий API 3x-ui: два пользователя,
  выдача, отзыв, включение, ротация и синхронизация ручных изменений панели;
- **Debian 12:** 32 unit/security-тестов в контейнере, не полная установка на VPS.

Ещё НЕ подтверждены:

- реальная установка и systemd на Debian 12 (эта платформа пока экспериментальная);
- PAK, bucket API и двухпользовательская изоляция на настоящем VK Cloud;
- полный путь «менеджер → VK → RX-PRO на Android», перезагрузка VPS и нагрузка.

CI включён: [workflow](.github/workflows/test.yml),
[пройденные установочные и интеграционные тесты](https://github.com/cwash797-cmd/RX-PRO-S3-Manager/actions/workflows/test.yml).
Ссылка на проверку точного release-коммита указывается в описании релиза.
**VK в автоматических тестах заменён моделью.** Проверка systemd использует
настоящий native core с локальным SOCKS, а не трафик через облако. Поэтому эти
результаты не доказывают доступность PAK и Android end-to-end на настоящем VK.
При тестировании была обнаружена и исправлена несовместимость пути credentials
с systemd 249 в Ubuntu 22.04; после исправления обе Ubuntu прошли установочные тесты.

## Что делает первая версия

Команда `sudo rxs3` открывает меню:

1. Добавление пользователя с квотой VPN-трафика и сроком.
2. Список, ссылка и терминальный QR.
3. Отключение, включение с новой ссылкой, ротация, удаление.
4. Синхронизация с панелью и восстановление прерванных операций.
5. Диагностика без ключей, URL панели и имён пользователей.
6. Зашифрованная копия реестра/конфигурации менеджера.
7. Очистка точных префиксов полностью отключённого пользователя.
8. Инструкция по обновлению из проверенного локального release-архива.

На каждого пользователя выдаются отдельные UUID и префикс поколения:

```text
rxs3/<installation-id>/<user-id>/g<generation>/
```

Внутри поколения используются **две разные PAK-пары**: для Android и bridge.
Административный ключ облака не передаётся ни в Android, ни в процесс bridge.
Bridge запускается отдельной `rxs3-bridge@<id>.service` с DynamicUser и
LoadCredential. Сервисы `s3-rixxx@...` не трогаются.

Отключение независимо пытается остановить bridge, отключить клиента панели и
отозвать PAK. Полный успех требует проверки отсутствия PAK в списке и отказа
авторизации прежнего ключа, если его секрет был получен. Потерянный ответ создания
согласуется по заранее записанному имени ключа. При ошибке остаётся явное состояние
`revocation_pending`, а не сообщение об успешном удалении.

Включение после отзыва требует **новой ссылки**. Ручное включение в панели не
восстанавливает отозванные PAK. Подтверждённые удаление, отключение, исчерпание
квоты и абсолютный срок переносятся из панели при синхронизации. Сбой API не
приравнивается к пустому списку. Конфликт UUID/привязки не разрешается удалением
чужого клиента: bridge останавливается, облачные ключи отзываются, запись остаётся
для ручного разбора. Автовосстановление `creating` никогда не выдаёт новый доступ.

## Поддерживаемая первая платформа

Цель установщика: обычная **Ubuntu 22.04/24.04 или Debian 12, x86_64, systemd**.
Не Docker, не ARM. Желательно начинать с Ubuntu 24.04 на новой VPS.
Существующая панель — стандартные пути `/usr/local/x-ui`, версия ровно 3.9.0.
Другая версия или нестандартная установка требуют отдельной проверки, а не
автоматического обновления панели. Бинарники загружаются с GitHub по закреплённым
SHA256; upstream shell-installers не запускаются.

На чистом сервере 3x-ui сначала настраивается в private network namespace:
генерируются пароль и base path, webListen становится 127.0.0.1, подписки
выключаются. Только затем запускается обычный `x-ui.service`. Если `unshare --net`
недоступен, безопасный bootstrap не обходится публичным запуском.

При подключении существующей панели её пароль, webListen, подписки, WS и другие
inbound не изменяются. Создаётся отдельный loopback VLESS TCP inbound с VLESS
Encryption. Firewall, SSH, nginx и Caddy не настраиваются.

**Нет нового публичного VPN-порта.** Внутренний `11600` из XDRIVE-конфигурации не
нужно открывать в firewall. HTTPS-подписки и iOS отложены.

## Подготовка VK Cloud

Один раз вручную:

1. Создайте/выберите проект VK Cloud с оплатой.
2. Выберите Object Storage **Москва / ru-msk**.
3. Создайте **отдельную учётную запись Object Storage** только для менеджера.
4. Сохраните Access Key ID и Secret Key; секрет показывается только при создании.
5. Используйте отдельный приватный бакет Hotbox/STANDARD или разрешите мастеру
   создать новый. Не включайте versioning, Object Lock, website/CDN, публичные ACL
   и bucket policy. Первая версия намеренно отвергает любую bucket policy.

Существующий рабочий бакет и его ключи для первых тестов не используйте.
PAK — собственный API VK, не AWS IAM:
<https://cloud.vk.ru/docs/ru/storage/s3/api/pak>.

Ключи вводятся скрыто с терминала. Не помещайте их в команды, историю shell,
скриншоты, GitHub Issues или сообщения поддержки. Ввод не отображает даже звёздочки —
это нормально; вставьте значение один раз и нажмите Enter.

## Установка прямо с GitHub — одна вставка на VPS

Репозиторий **публичный**. GitHub-токен, вход в браузер, SCP/SFTP и ручной перенос
папок больше не нужны. Для первого теста выберите **новую Ubuntu 24.04 x86_64 с
systemd**, желательно с 2 GiB RAM. Не начинайте с рабочего сервера.

Подключитесь к VPS по SSH и вставьте блок целиком:

```bash
sudo apt-get update && sudo apt-get install -y curl ca-certificates && (
  set -e
  f="$(mktemp)"
  trap 'rm -f "$f"' EXIT
  curl -fsSL --proto '=https' https://raw.githubusercontent.com/cwash797-cmd/RX-PRO-S3-Manager/main/get.sh -o "$f"
  sudo bash "$f"
)
```

Скрипт сам установит зависимости, скачает **опубликованный и проверенный
0.1.0-rc1**, проверит закреплённый SHA256 архива и внутренний manifest,
распакует во временную папку, установит 3x-ui **3.9.0**, затем откроет мастер
настройки и русское меню. Скачивается не непроверенный код ветки main.
При несовпадении SHA256 установка останавливается. Временные файлы удаляются.

Полный скрипт сначала скачивается в файл и только потом запускается; вариант
`curl | bash` не нужен и не поддерживается, поскольку мастер читает ввод с терминала.
В опубликованном rc1 ничего не заменено: добавлен только удобный способ его загрузки.
У быстрого загрузчика дополнительно проверены отказ при повреждении архива,
защита существующей папки, очистка временных файлов и требования к терминалу.

Если 3x-ui уже установлена, скрипт по умолчанию остановится, не заменяя её.
Для подключения **существующей совместимой 3x-ui 3.9.0** сначала сохраните её
резервную копию и проверьте WS; затем используйте тот же блок, заменив строку
`sudo bash "$f"` на:

```bash
  sudo bash "$f" --existing-panel
```

После установки для повторного открытия меню достаточно:

```bash
sudo rxs3
```

### Если хочется проверить файлы до установки

Можно отдельно скачать `get.sh`, просмотреть его и выполнить
`bash get.sh --download-only ./rxs3-reviewed` с новым, ещё не существующим
каталогом. Этот режим только скачивает, сверяет SHA256 и распаковывает релиз,
не ставит пакеты и не меняет систему. Не используйте автоматический GitHub
«Source code» как установочный архив: в нём нет обязательного manifest.

Мастер попросит URL панели с её base path и admin API token. Создать отдельный
токен можно штатной CLI панели (вывод содержит секрет):

```bash
sudo /usr/local/x-ui/x-ui setting -getApiToken -tokenName rxs3-manager-unique -tokenScope admin
```

Не запускайте эту команду повторно с тем же именем без необходимости: она
перевыпускает токен. Менеджер не редактирует SQLite панели напрямую.

Для новой панели `sudo rxs3 panel-info` показывает локальный URL/логин/пароль
только в терминале. На своём компьютере создайте SSH-туннель (если порт 2053):

```bash
ssh -L 2053:127.0.0.1:2053 root@IP_VPS
```

Откройте показанный менеджером URL `http://127.0.0.1:2053/<base-path>/` в браузере.
Не открывайте 2053/2096/10001 наружу ради менеджера.

## Первая проверка на чистом сервере и настоящем VK

1. `sudo rxs3 diagnose`: проверить API панели, inbound, приватность бакета,
   доступность PAK и таймер. Не отправлять `config.json` в поддержку.
2. Добавить **двух** тестовых пользователей с разными именами. Выдача сама
   проверяет PUT/GET/LIST/DELETE обоими полученными PAK.
3. Импортировать ссылку первого в официальный RX-PRO 1.6.0. Проверить внешний IP,
   сайт и Telegram. Затем проверить второго.
4. Отключить первого: его уже работающая сессия должна оборваться; второй должен
   продолжить работу. Если отзыв pending, не считать шаг успешным.
5. Включить первого и передать новую ссылку. Старая не должна работать.
6. Проверить ротацию, удаление и отражение отключения/удаления из панели после
   `sudo rxs3 sync` (таймер обычно запускается примерно раз в минуту).
7. Проверить зашифрованную копию, повторную установку **без** `--fresh-panel`,
   затем перезагрузку VPS. Сравнить состояние пользователей и обычного WS.
8. Следить за расходами Object Storage. Квота 3x-ui — **не лимит оплаты S3**.

Если что-то не проходит, остановитесь на этом шаге. Сообщите ОС, этап и короткую
ошибку менеджера; после завершённого setup можно прислать `sudo rxs3 diagnose`.
Не присылайте ссылку/QR, `config.json`, `setup.json`, `state.sqlite`, runtime-файлы
или пароль резервной копии. `revocation_pending` означает НЕЗАВЕРШЁННЫЙ отзыв:
повторите `sudo rxs3 sync` после восстановления API, не удаляя реестр вручную.

Нагрузка и количество пользователей на VPS пока не измерены. Каждому bridge
назначен MemoryMax 256 MiB, а не гарантия, что сервер выдержит много экземпляров.
До успешной проверки реального VK не выдавайте платный/массовый доступ.

## Резервные копии и восстановление

```bash
sudo rxs3 backup /root/manager_2026-10-06.rxs3-backup
sudo rxs3 restore-quarantine /root/manager_2026-10-06.rxs3-backup /root/rxs3_quarantine
```

Пароль вводится скрыто, минимум 12 символов. Используются scrypt и AES-256-GCM с
новыми salt/nonce; архив аутентифицируется до разбора JSON. Plaintext tar не создаётся.

Это копия **конфигурации и реестра менеджера**, не полный образ VPS и не резервная
копия БД 3x-ui. Базу панели сохраняйте отдельно штатными средствами 3x-ui.
Восстановление — только в новый **офлайн-каталог карантина**; оно ничего не
запускает и не меняет в панели/облаке. Старой копии неизвестны выпущенные позднее
ключи. Не копируйте её поверх работающего `/var/lib/rxs3` и не ожидайте автоматической
миграции на другой VPS. Автоматическое безопасное применение карантина к живой
установке в rc1 не реализовано: требуется сверка с текущей панелью и списком PAK.

## Разработка и лицензии

```bash
python3 -m unittest discover -s tests -v
python3 build_release.py
```

`tests/integration_panel.py` требует закреплённые реальные бинарники в `.lab/x-ui`
и отдельный network namespace. `tests/installed_smoke.py` изменяет системные
пути **только на специально разрешённом одноразовом CI runner**; не запускайте на VPS.

Код генератора профилей взят из RX-PRO/S3-RIXXX (GPL-3.0). Xray и зависимости
скачиваются отдельно; их лицензии сохраняются в `/opt/rxs3/licenses`.
Секреты не должны попадать в Git, CI artifacts и публичные сообщения.
